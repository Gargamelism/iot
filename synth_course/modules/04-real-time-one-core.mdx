## Goal

Structure the firmware so audio can never miss a deadline on a single core shared with
everything else, and know your exact CPU budget.

## You'll be able to

- Create and prioritize FreeRTOS tasks on the ESP32-C3, and predict who runs when.
- Explain why the audio thread must never block on anything but the audio device.
- Measure CPU load with the cycle counter and reason in cycles per frame.
- Share parameters between `loop()` and the audio task without priority problems.
- Recognize and diagnose a task watchdog reset.

## Concepts

- **The budget.** 160 MHz / 44.1 kHz ≈ **3,628 cycles per output frame**, for everything.
- **FreeRTOS on one core.** Tasks, priorities and preemption. `loop()` is just a task too. A
  max-priority audio task runs until it *blocks* (on the I2S write). Only then do lower
  priorities, including IDLE, run.
- **The task watchdog.** If IDLE never runs, the watchdog bites: `Task watchdog got
  triggered … IDLE0`.
- **Blocks and latency.** Audio is produced in blocks. Block length is the control
  granularity and part of the latency, and per-block overhead gets spread across it.
- **Real-time rules** (Bencina). In the audio callback: no locks you can wait on, no
  allocation, no I/O, no unbounded loops.
- **Sharing data.** A mutex with a *zero* timeout on the audio side (use last block's values
  if busy). A lock-free alternative is double buffering. Related values must be published
  together.
- **Priority inversion**, and why a zero-timeout take sidesteps it.
- **Measuring.** `esp_cpu_get_cycle_count()` around the block's compute, divided by the
  number of frames.

## Build

Start from module 03's tone.

**Add:**

- **An audio task.** Move the block generation and write into a task pinned to core 0 at the
  highest priority. `loop()` now only blinks the LED and prints. *Example* (illustrative):

  ```cpp
  xTaskCreatePinnedToCore(audioTask, "audio", 4096, nullptr,
                          configMAX_PRIORITIES - 1, nullptr, 0);
  ```
- **A load meter.** Time each block's compute with the cycle counter and report it about once
  a second (from `loop()`, not from the audio task). *Example:*

  ```
  audio: 412 cyc/frame (11.4% of 3628), block 256 = 5.80 ms
  ```
- **A parameter handoff.** A struct of the parameters the audio task needs, written by `loop()`
  and read by the audio task once per block, never waiting. *Example:* `loop()` alternates the
  frequency between 440 and 660 Hz every 2 s.
- **A broken version, then the fix.** Temporarily make the audio task spin, for example by
  writing nothing and looping. Capture the watchdog output. *Example:*

  ```
  E (5123) task_wdt: Task watchdog got triggered. The following tasks did not reset the watchdog in time:
  E (5123) task_wdt:  - IDLE0 (CPU 0)
  ```

**Constraints:**

- The audio contract (see the curriculum), from now on and for every module.
- If an I2S write ever comes back short, the task must not spin. Make sure it yields.
- Stack size: justify the number.

**Deliverable:** the task-based skeleton every later module builds on.

## Design questions

1. If the audio task is at the highest priority and the C3 has one core, when exactly does
   `loop()` run? How does that interact with polling an encoder (module 05)?
2. Mutex with zero timeout, or a lock-free double buffer? What does each cost and what can go
   wrong?
3. If `write()` returns fewer bytes than asked, what's the safest thing to do on the audio
   task?
4. How would you know you're at 90% load before it fails audibly?

## Compare (spoiler)

- `synth/audio_task.cpp` `audioTaskBegin()`: `xTaskCreatePinnedToCore(audioTask, "audio",

  the per-voice arrays.
